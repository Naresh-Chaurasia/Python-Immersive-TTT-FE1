== Overview

This guide explains how to run the *Company Knowledge Assistant* RAG application *without Docker* — directly on your local machine with locally installed PostgreSQL, Redis, and Python.

NOTE: This guide includes commands for both *macOS* (using Homebrew) and *Windows* (using PowerShell / winget / installers). Each command block is labeled and commented to indicate which OS it applies to. If a command works the same way on both platforms (e.g. `psql`, `curl`, `pip`), it is shown once without an OS-specific label.

== Prerequisites

Before starting, ensure you have the following installed on your machine:

* *Homebrew* (macOS package manager) — https://brew.sh +
  *Windows equivalent:* https://chocolatey.org[Chocolatey] or https://learn.microsoft.com/en-us/windows/package-manager/winget/[winget] (built into Windows 10/11)
* *Python 3.11+* — Check with `python3 --version` (macOS) or `python --version` (Windows)
* *PostgreSQL 17* (with pgvector extension)
* *Redis* (native on macOS via Homebrew; on Windows, Redis is typically run via Docker or WSL — see notes below)
* An *OpenAI API key* (with access to `text-embedding-3-small` and `gpt-4o-mini`)
* (Optional) A *Cohere API key* for reranking
* *(Windows only)* https://gitforwindows.org[Git Bash] or *WSL2 (Windows Subsystem for Linux)* is recommended for a smoother experience, since many `brew`-based steps have simpler equivalents on Linux/WSL than native PowerShell.

=== Install PostgreSQL 18 with pgvector

// macOS (Homebrew)
[source,bash]
----
# Install PostgreSQL 18
brew install postgresql@18

# Start PostgreSQL as a background service
brew services start postgresql@18

/opt/homebrew/opt/postgresql@18/bin/pg_ctl \

  -l /opt/homebrew/var/postgresql@18/server.log start


# Install pgvector extension
brew install pgvector

# Verify PostgreSQL is running

Expected output: `/tmp/.s.PGSQL.5432 - accepting connections`

// Windows (PowerShell)
[source,powershell]
----
# Option 1: Install via winget (recommended)
winget install -e --id PostgreSQL.PostgreSQL.16

# Option 2: Install via Chocolatey (if you use Chocolatey instead of winget)
choco install postgresql16 --params '/Password:postgres'

__3. To stop all related services__ (PostgreSQL, Redis Stack, and the app):


----
Redis Stack runs as a Docker image because __Homebrew does not provide a `redis-stack` formula that can be installed directly via `brew install`__.

The regular Homebrew Redis (`brew install redis`) is a minimal Redis server that does __not__ include the RediSearch module. The `langchain-redis` package's `RedisSemanticCache` depends on RediSearch's `FT._LIST` command, which is only available in the Redis Stack distribution.

There is no `brew install redis-stack` alternative — only a `redis-insight` GUI cask exists via Homebrew. The official installation method for Redis Stack on macOS is either:

1. __Docker__ (the approach we're using): `docker run -d --name cka-redis -p 6379:6379 redis/redis-stack:latest`
2. __Direct download__ from redis.com: Download and run the Redis Stack server binary manually

So Docker is the simplest and cleanest way to get Redis Stack running locally. If you'd like to avoid Docker for Redis, there are two alternatives:

__Option A: Disable Redis semantic caching__ — Remove or comment out the `RedisSemanticCache` block in `app/rag.py` (lines 39-45). The app will work without caching, just without the performance benefit of cached responses for semantically similar questions.

__Option B: Use a simpler Redis cache__ — Replace `RedisSemanticCache` with a basic TTL-based Redis cache that doesn't require RediSearch.

Would you like me to proceed with either of these alternatives to eliminate the Docker dependency?

----

```bash
# Stop the app
lsof -ti:8000 | xargs kill -9

# Stop Redis Stack container
docker run -d --name cka-redis -p 6379:6379 -p 8001:8001 redis/redis-stack:latest
docker stop cka-redis
docker rm cka-redis

# Stop PostgreSQL (optional)
brew services stop postgresql@18
```

Delete existing data from the `langchain_pg_embedding` table (which stores all document chunks, embeddings, and metadata). Connect to PostgreSQL and run:

// macOS / Linux / Windows — psql syntax is identical everywhere
[source,bash]
----
psql -U postgres -d postgres -c "TRUNCATE TABLE langchain_pg_embedding;"
----

Or, if you also want to remove the HNSW index and recreate everything from scratch:

// macOS / Linux
[source,bash]
----
psql -U postgres -d postgres -c "SELECT * FROM langchain_pg_embedding;"
psql -U postgres -d postgres -c "DROP TABLE IF EXISTS langchain_pg_embedding CASCADE;"
psql -U postgres -d postgres -f init-db/init.sql
----

// Windows (PowerShell) — same commands, backslash path for -f
[source,powershell]
----
psql -U postgres -d postgres -c "SELECT * FROM langchain_pg_embedding;"
psql -U postgres -d postgres -c "DROP TABLE IF EXISTS langchain_pg_embedding CASCADE;"
psql -U postgres -d postgres -f init-db\init.sql
----

The `TRUNCATE` approach is faster — it clears all rows but keeps the table structure and indexes intact.

*Step 2: Clear the Redis Cache (Optional)

If you want to also clear cached LLM responses from the semantic cache:

// macOS / Linux / Windows — redis-cli syntax is identical (Windows via Docker/WSL/Memurai)
[source,bash]
----
redis-cli FLUSHDB
----

*Step 3: Re-run Ingestion*

Start the app (if not already running):

// macOS / Linux
[source,bash]
----
uvicorn app.api:app --host 0.0.0.0 --port 8000 --reload
----

// Windows (PowerShell) — identical command, just run from the activated venv
[source,powershell]
----
uvicorn app.api:app --host 0.0.0.0 --port 8000 --reload
----

Then trigger ingestion:

// macOS / Linux
[source,bash]
----
curl -X POST http://localhost:8000/ingest
----

// Windows (PowerShell)
[source,powershell]
----
curl.exe -X POST http://localhost:8000/ingest
# or: Invoke-RestMethod -Method POST -Uri http://localhost:8000/ingest
----

Monitor the status:

// macOS / Linux
[source,bash]
----
curl http://localhost:8000/ingest/status
----

// Windows (PowerShell)
[source,powershell]
----
curl.exe http://localhost:8000/ingest/status
# or: Invoke-RestMethod -Uri http://localhost:8000/ingest/status
----

Wait until you see `"status":"succeeded"` with document/chunk counts.

*Step 4: Verification After Ingestion*

Check that the table has data:

// macOS / Linux / Windows — identical psql command
[source,bash]
----
psql -U postgres -d postgres -c "SELECT COUNT(*) FROM langchain_pg_embedding;"

You should see the chunk count (e.g., ~300 rows).

=== `app/api.py` — FastAPI Application

The main web server with the following endpoints:

==== `GET /`
Serves the static `index.html` frontend page.

==== `POST /ingest`
Starts document ingestion as a **background async task**.

- Uses an `asyncio.Lock` to prevent concurrent ingestion jobs.
- Returns HTTP 409 if ingestion is already running.
- The background job updates a shared `_ingest_last` dict tracking status (`idle`, `running`, `succeeded`, `failed`), timestamps, statistics, and error messages.

==== `GET /ingest/status`
Returns the current state of the ingestion process (status, stats, timestamps, error info).

==== `POST /ask`
Accepts a JSON body `{"question": "..."}` and runs the full RAG pipeline:

1. Calls `answer_with_docs_async()`.
2. By default filters results to the `"guides"` category (hard-coded but easy to change).
3. Returns `{answer, sources, contexts}`.

The application also:
- Mounts static files at `/static`.
- Logs execution time for each `/ask` request.

=== `app/ingest.py` — Document Ingestion Pipeline

The ingestion process follows these steps:

==== Step 1: Load Documents (`_load_docs()`)
- Recursively scans the `DATA_DIR` directory for supported file types.
- Uses category-specific loaders from LangChain community:
  - `.md` → `UnstructuredMarkdownLoader`
  - `.pdf` → `PyMuPDFLoader`
  - `.docx` → `UnstructuredWordDocumentLoader`
  - `.txt` → `TextLoader`
- Tags each document with a `category` metadata field derived from its parent folder name (e.g., `data/guides/file.md` → `category="guides"`).
- Skips directories and hidden files.
- Errors on individual files are caught and logged without stopping the pipeline.

==== Step 2: Chunk Documents (`_chunk()`)
- Uses `RecursiveCharacterTextSplitter` from LangChain.
- `chunk_size=900` characters per chunk.
- `chunk_overlap=120` characters between consecutive chunks to maintain context continuity.

==== Step 3: Store Embeddings
- Connects to the PostgreSQL vector store via `get_vector_store()`.
- Generates embeddings for each chunk using OpenAI's `text-embedding-3-small`.
- Asynchronously stores the embeddings + metadata in the `langchain_pg_embedding` table.

==== Step 4: Create Vector Index (`_create_index()`)
- Creates an **HNSW** (Hierarchical Navigable Small World) index for efficient approximate nearest-neighbor search.
- Uses **cosine distance** as the similarity metric.
- Configuration: `m=16` (connections per node), `ef_construction=64` (index quality).

The function returns a dict with `{documents: N, chunks: N}` statistics.

=== `app/rag.py` — RAG Retrieval + Generation Chain

==== System Prompt
The LLM is instructed to:
- Answer strictly based on the provided context.
- Reply "I don't know" if the answer is not in the context.
- Prefer the most recent policy by effective date when conflicts exist.

==== Chain Construction (`_build_chain()`)

1. **Vector Store** — Connect to PostgreSQL vector store.
2. **Retriever** — Configured with:
   - `k=5` documents retrieved (configurable via `RETRIEVAL_K` env var).
   - Optional metadata filter by category (e.g., only search "guides").
3. **Reranker** — Uses Cohere `rerank-multilingual-v3.0` to reorder the 5 retrieved chunks, keeping the top 3 (`top_n=3`). This improves retrieval precision.
4. **LLM** — OpenAI `gpt-4o-mini` for cost-effective, fast generation.
5. **Chain** — Uses LangChain's `create_stuff_documents_chain` (stuff all context into prompt) wrapped by `create_retrieval_chain`.

==== 📍 When Does Reranking Happen? Is it a Separate API Call?

Yes — Cohere reranking happens **after** vector retrieval but **before** the LLM ever sees the context, and it is a completely separate, external network call to Cohere's servers (distinct from both the OpenAI embeddings call and the OpenAI chat completion call).

*Why it's a distinct API call*

`CohereRerank(top_n=3, model="rerank-multilingual-v3.0")` is a LangChain wrapper around Cohere's own `POST /v1/rerank` REST endpoint. It requires its own API key (`CO_API_KEY`, read from the environment — see the `.env` table above) and talks to Cohere's infrastructure using the `cohere` Python SDK/HTTP client. This is entirely separate from OpenAI, which handles embeddings and answer generation.

In `_build_chain()`, the reranker is wired in via `ContextualCompressionRetriever`:

[source,python]
----
base_retriever = store.as_retriever(search_kwargs=search_kwargs)

compressor = CohereRerank(
    top_n=3,
    model="rerank-multilingual-v3.0",
)

retriever = ContextualCompressionRetriever(
    base_retriever=base_retriever,
    base_compressor=compressor,
)
----

*Step-by-step order of API calls for a single `/ask` request*

1. **OpenAI Embeddings API** — the user's question is embedded (`text-embedding-3-small`) so it can be compared against stored vectors.
2. **pgvector similarity search** — `base_retriever` queries PostgreSQL/pgvector and returns the top `k` (default 5) most similar chunks. No LLM/reranker call is involved here — it's pure vector math inside Postgres.
3. **Cohere Rerank API** — `ContextualCompressionRetriever` calls `compressor.compress_documents(documents, query)`, which sends the question text plus the 5 candidate chunks to Cohere's rerank model. Cohere scores each chunk's relevance to the actual question and returns them reordered; LangChain keeps only the top 3 (`top_n=3`).
4. **OpenAI Chat Completion API** — only after reranking completes does `create_stuff_documents_chain` insert the reranked top-3 chunks into the `PROMPT` and call `gpt-4o-mini` to generate the final answer.

So the full sequence is:

[source]
----
User Question
   ↓
OpenAI Embedding API (embed the question)
   ↓
pgvector similarity search (k=5 candidates from Postgres)
   ↓
Cohere Rerank API (separate external call → top_n=3)
   ↓
Prompt assembly (stuff top-3 chunks into PROMPT)
   ↓
OpenAI Chat Completion API (gpt-4o-mini generates the answer)
   ↓
Final Answer
----

**Key takeaway:** Reranking is *not* a manual step you'd find as separate code elsewhere in `rag.py` — it's encapsulated inside the single `retriever` object (`ContextualCompressionRetriever`) that `create_retrieval_chain` invokes. That one `retriever.invoke()` call internally performs both the vector search step and the Cohere rerank network call, in that order, before the doc chain ever runs the LLM. A single `/ask` request therefore triggers three distinct external API round-trips in sequence: OpenAI (embeddings) → Cohere (rerank) → OpenAI (chat completion).

==== Semantic Caching (DISABLED)
- `RedisSemanticCache` was previously used to cache LLM responses based on
  embedding similarity between questions, with `distance_threshold=0.98`.
- **Bug found:** a `distance_threshold` of `0.98` is far too permissive.
  In practice this caused **completely unrelated questions** (e.g. a PTO
  question and a travel-policy question) to be treated as "similar enough,"
  so the cache incorrectly returned a previously cached answer for a
  different question entirely — silently giving users the wrong answer.
- **Fix:** semantic caching has been **disabled** in `app/rag.py` via
  `set_llm_cache(None)`. The `RedisSemanticCache` import/setup was removed.
  Every `/ask` call now always generates a fresh answer from the LLM using
  the freshly retrieved context, eliminating the risk of stale/incorrect
  cached answers.
- Redis is therefore **no longer required** for the app to function
  correctly. It was previously used only for this semantic cache.
- If semantic caching is reintroduced in the future, use a much stricter
  `distance_threshold` (e.g. `0.05`–`0.15`, since `langchain-redis` treats
  this value as a *distance* where lower = stricter/more-similar match
  required) and thoroughly test with dissimilar questions before relying
  on it in production.

=== `init-db/init.sql`

PostgreSQL initialization script that runs automatically when the Postgres container starts for the first time:

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE IF NOT EXISTS langchain_pg_embedding (
    langchain_id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    content text,
    embedding vector(1536),
    langchain_metadata jsonb,
    category text
);
```

- Enables the `vector` extension (required by pgvector).
- Creates the `langchain_pg_embedding` table with:
  - `langchain_id` — UUID primary key.
  - `content` — The raw text of the chunk.
  - `embedding` — 1536-dimensional vector (OpenAI `text-embedding-3-small` dimension).
  - `langchain_metadata` — JSONB for flexible metadata.
  - `category` — Direct column (also indexed via metadata_columns in LangChain).

==== What is `langchain_metadata` Used For?

`langchain_metadata` is a `jsonb` column in the `langchain_pg_embedding` table that stores **arbitrary, flexible per-chunk metadata as JSON**, separate from the actual embedding vector and raw text content columns.

*Where it's defined*

- `init-db/init.sql`: `langchain_metadata jsonb` — declared as a JSONB column in the table schema.
- `app/utils.py` (`get_vector_store()`): passes `metadata_json_column="langchain_metadata"` to `AsyncPGVectorStore.create()`, telling LangChain which column to use for reading/writing metadata.

*What goes into it*

During ingestion (`app/ingest.py`), every `Document` object loaded from a file (PDF/MD/DOCX/TXT) carries a `.metadata` dict. For example:

[source,python]
----
d.metadata["category"] = category   # e.g. "guides", "policies"
----

Document loaders such as `PyMuPDFLoader` also automatically attach fields like `source` (the file path) and page numbers. When `store.aadd_documents(chunks)` runs during ingestion, LangChain serializes each chunk's entire `.metadata` dict into JSON and writes it into the `langchain_metadata` column — one JSON blob per row/chunk.

*Why it's useful*

1. **Flexible schema** — new metadata fields (source, page, author, date, etc.) can be added without altering the table schema, since it's just JSON.
2. **Citations/traceability** — in `app/rag.py`'s `answer_with_docs_async()`, each retrieved document's `d.metadata.get("source")` is read to build the `sources` list returned to the user, so they can see which file(s) an answer came from. This value comes straight out of the `langchain_metadata` JSON blob.
3. **Filtered search support** — `metadata_columns=["category"]` in `utils.py` promotes the `category` key specifically out of the JSON blob into its own indexed `category` SQL column (separate from `langchain_metadata`), enabling fast `WHERE category = 'guides'` filtering during vector search (see `_build_chain()`'s `search_kwargs["filter"] = {"category": category}`).

**Summary:** `langchain_metadata` is the general-purpose JSON "extra info" bucket for each embedded chunk (source file, page, etc.), while frequently-filtered fields like `category` are additionally promoted to their own real column for efficient querying — both are populated automatically by LangChain's vector store during ingestion.

=== pgvector

`pgvector` is the PostgreSQL extension that powers the entire vector storage and semantic search in this project. Here's where it's used:

*Infrastructure Layer*

- *`docker-compose.yml`*: The PostgreSQL container uses the `pgvector/pgvector:pg17` image which comes with pgvector pre-installed.
- *`init-db/init.sql`*: Enables the `vector` extension in PostgreSQL on database creation.
- *PostgreSQL table `langchain_pg_embedding`*: This is the actual table created by `AsyncPGVectorStore` that stores:
  - The *embedding vectors* (1536-dimensional floats from `text-embedding-3-small`)
  - Document chunk *text content*
  - *Metadata* (category, source, etc.)

*Application Layer* — `app/utils.py`
- *`AsyncPGVectorStore`* (line 46-61) is the Python abstraction over the pgvector-backed table. It handles:
  - Converting text to vectors via the embedding model
  - Storing vectors in PostgreSQL
  - Performing *cosine similarity search* using pgvector's internal operations

*Ingestion* — `app/ingest.py`
- *`store.aadd_documents(chunks)`* (line 184): Embeds document chunks and stores them as vectors in pgvector.
- *HNSW index creation* (lines 130-152): Creates a pgvector-compatible Hierarchical Navigable Small World index on the vector column to accelerate approximate nearest-neighbor search.

*Retrieval* — `app/rag.py`
- *`store.as_retriever()`* (line 140): Creates a retriever that queries pgvector for the most semantically similar chunks to the user's question.

Data Flow Summary

```
User Question → OpenAI Embedding (1536-d vector) → pgvector similarity search → 
Top-k chunks → Cohere Rerank → LLM → Answer
```

So *`pgvector` is the vector database* that makes semantic search possible — without it, the RAG pipeline would have no way to find relevant document chunks for a given question.

Your PostgreSQL user might need a password or the correct permissions. Try:

// macOS / Linux / Windows — psql syntax is identical
[source,bash]
----
# Set a password for postgres user
psql -d postgres -c "ALTER USER postgres PASSWORD 'postgres';"

# Then update .env to use password authentication
# DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/postgres
----

Or if your macOS user is the PostgreSQL superuser:

// macOS / Linux
[source,bash]
----
# Use trust authentication — update .env to:
DATABASE_URL=postgresql+asyncpg://YOUR_USERNAME@localhost:5432/postgres
----

// Windows (PowerShell) — use your Windows username instead
[source,powershell]
----
# Update .env to:
DATABASE_URL=postgresql+asyncpg://YOUR_USERNAME@localhost:5432/postgres
----

Where `YOUR_USERNAME` is the output of `whoami` (macOS/Linux) or `$env:USERNAME` / `whoami` (Windows PowerShell).

== Key Design Decisions

1. **Async everywhere** — All I/O operations (DB queries, API calls, file loading) are asynchronous using `asyncio`, ensuring the server remains responsive under concurrent requests.

2. **Background ingestion** — Document ingestion runs as a background task, so the API remains available during processing. A lock prevents concurrent ingestion jobs.

3. **Metadata filtering** — Documents are categorized by source folder, enabling filtered retrieval by category (e.g., only search "policies" or "guides").

4. **Reranking** — Using Cohere's reranker after initial vector retrieval improves precision by re-ranking the top-k results, ensuring only the most relevant contexts are fed to the LLM.

5. **Semantic caching (DISABLED)** — Redis Semantic Cache was originally added to avoid redundant LLM calls for semantically similar questions. However, a `distance_threshold=0.98` proved far too permissive and caused unrelated questions (e.g. PTO vs. travel policy) to incorrectly return each other's cached answers. Semantic caching has since been **disabled** (`set_llm_cache(None)` in `app/rag.py`) so every question is always answered fresh — correctness was prioritized over caching performance.


6. **Category-based retrieval** — The `/ask` endpoint currently hard-codes `category="guides"`, demonstrating filtered search. This can be parameterized for production use.

7. **Evaluation framework** — RAGAS integration allows quantitative measurement of RAG quality, essential for iterating on the pipeline.

== Q&A

*Briefly explain the use of #PGVectorStore#*

*PGVectorStore Usage in `utils.py`*

The file uses __`AsyncPGVectorStore`__ (from `langchain_postgres`) to provide a PostgreSQL-backed vector database for the RAG knowledge management system. Here's how it's used:

*1. __Database Connection Setup (lines 18-24)__*

- Reads the `DATABASE_URL` environment variable (a PostgreSQL connection string using the `asyncpg` driver).
- Creates a `PGEngine` from this connection string, which manages the async database connection pool.

*2. __Embedding Model Initialization (line 29)__*

- Initializes OpenAI's `text-embedding-3-small` model to convert text into vector embeddings.

*3. __`get_vector_store()` Factory Function (lines 33-63)__*

- An async factory function that creates and returns an `AsyncPGVectorStore` instance configured with:

  - __`engine`__: The PostgreSQL connection engine.
  - __`embedding_service`__: The OpenAI embedding model for vector generation.
  - __`table_name`__: `"langchain_pg_embedding"` — the database table that stores the vector embeddings.
  - __`metadata_json_column`__: `"langchain_metadata"` — a JSON column for storing arbitrary document metadata alongside each vector.
  - __`metadata_columns`__: `["category"]` — specific metadata fields extracted from the JSON column that can be used as filters during similarity search.

*Purpose in the RAG System*

The `AsyncPGVectorStore` serves as the __vector storage and retrieval layer__ for the RAG pipeline. It:

- Stores document chunks as vector embeddings in PostgreSQL (using the `pgvector` extension).
- Enables __semantic similarity search__ — given a query, it finds the most semantically relevant document chunks by comparing vector distances.
- Supports __metadata filtering__ (by `category`) to narrow down search results.
- Uses __async operations__ for non-blocking database access, suitable for the FastAPI application.

*#Ingestion#*


You're exactly right. Since you've already run ingestion, the vector embeddings and document metadata are stored **persistently** in the PostgreSQL database via the `pgvector` extension. The `AsyncPGVectorStore` plays two distinct roles here:

1. **Ingestion Phase** (run once) — via `ingest.py`
- Documents are split into chunks → embedded → stored into the `langchain_pg_embedding` table using `AsyncPGVectorStore`.
- This populates the database with vectors and metadata (e.g., category).

2. **Query/Retrieval Phase** (run many times) — via `rag.py` / `api.py`
- The same `AsyncPGVectorStore` (created by `get_vector_store()` in `utils.py`) connects to the **already-populated** `langchain_pg_embedding` table.
- It performs **similarity search** against the stored vectors — no re-embedding or re-storing of documents needed.
- The database persists the data across application restarts.

So the `PGVectorStore` provides **persistent, reusable storage** — you ingest once and query many times. The `AsyncPGVectorStore.create()` call in `utils.py` is idempotent in the sense that if the table already exists, it simply connects to it rather than recreating it (depending on the underlying LangChain implementation with `sync_mode="OFF"` and `create_extension=False` or similar flags). If you want to be explicit about not recreating the table, you could also use `AsyncPGVectorStore(engine=PG_ENGINE, ...)` directly instead of `.create()`.

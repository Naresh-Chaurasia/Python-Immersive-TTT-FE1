== Components involved

* `mcp_client.py` / `mcp_client_streamable_http.py` — Streamlit app, MCP client, LangChain agent (logs to `mcp_client.log`)
* `mcp_server.py` — FastMCP server exposing `wikipedia_search` and `ddg_search` tools over Streamable HTTP on port 8000 (logs to `mcp_server.log`)
* `gpt-4o` via `ChatOpenAI` — the LLM brain of the agent

NOTE: Both `mcp_client.py` and `mcp_client_streamable_http.py` write to the *same* file, `mcp_client.log` (`LOG_FILE = os.path.join(LOG_DIR, "mcp_client.log")` is identical in both). If you ran either/both, their entries interleave in one file — this alone can make the log look "busier" than expected.

== The short answer

One simple question triggers *three separate round-trip conversations*, each of which itself needs multiple HTTP requests:

. A **tool-discovery** MCP session (happens automatically, every Streamlit rerun) — 5 HTTP calls
. An **LLM decision call** to GPT-4o ("do I need a tool, and which one?") — 1 HTTPS call
. A **tool-invocation** MCP session (actually running `wikipedia_search`) — 6 HTTP calls
. An **LLM final-answer call** to GPT-4o ("here's the tool result, write the answer") — 1 HTTPS call

That's *13 network round trips* for one question, each wrapped in `Entering/Exiting method` trace logs — hence the volume.

== Step-by-step walkthrough (mcp_client.log lines 16-47)

=== Step 1 — Streamlit reruns the whole script (module-level code)

Streamlit re-executes the entire `.py` file top-to-bottom on *every* interaction (including submitting the text box). This means the MCP client is rebuilt and `get_tools()` is called again, even though nothing about the available tools has changed.

[source]
----
16  Entering method: __main__ (module execution start)
17  creating MultiServerMCPClient for server 'tools'
18  discovering MCP tools via client.get_tools()
19  httpx POST /mcp 200 OK          -> MCP "initialize" handshake
20  Received session ID: 00ce941a...
21  Negotiated protocol version
22  httpx POST /mcp 202 Accepted    -> "initialized" notification (fire-and-forget)
23  httpx GET  /mcp 200 OK          -> opens server->client SSE stream
24  httpx POST /mcp 200 OK          -> tools/list request (returns wikipedia_search, ddg_search)
25  httpx DELETE /mcp 200 OK        -> session torn down (one-off session)
26  discovered 2 MCP tool(s): ['wikipedia_search', 'ddg_search']
27  loading environment variables from .env file
28  creating ChatOpenAI llm instance
29  creating agent via create_agent(llm, tools)
30  rendering streamlit title
----

Matching `mcp_server.log`:
[source]
----
8   Created new transport with session ID: 00ce941a...
9   Processing request of type ListToolsRequest
10  Terminating session: 00ce941a...
----

This entire block (5 HTTP requests) runs *before* your question is even looked at — it is simply the cost of Streamlit's "rerun from top" execution model combined with `get_tools()` not reusing a persistent session.

=== Step 2 — Your task is processed

[source]
----
31  Entering method: on_task_submitted(task='what is salsa dance')
32  invoking agent.ainvoke() with task
----

=== Step 3 — LLM call #1: "decide what to do"

[source]
----
33  httpx2 POST https://api.openai.com/v1/chat/completions 200 OK   (~2.5s)
----

The agent sends your question + the list of available tools (their names/schemas) to GPT-4o. GPT-4o replies with a *tool call* decision: "call `wikipedia_search` with query='Salsa dance'". No tool has executed yet — this is just the LLM's decision.

=== Step 4 — A brand-new MCP session is opened to actually run the tool

Because `load_mcp_tools()` doesn't keep a persistent session alive, the LangChain tool wrapper opens **another fresh MCP session** just to call `wikipedia_search`:

[source]
----
34  httpx POST /mcp 200 OK          -> initialize handshake (2nd session)
35  Received session ID: b4115821...
36  Negotiated protocol version
37  httpx POST /mcp 202 Accepted    -> initialized notification
38  httpx GET  /mcp 200 OK          -> SSE stream opened
39  httpx POST /mcp 200 OK          -> CallToolRequest sent (wikipedia_search)
40  httpx POST /mcp 200 OK          -> (~3.85s later) a follow-up ListToolsRequest
41  httpx DELETE /mcp 200 OK        -> session torn down
----

Matching `mcp_server.log` — this is where the real work happens:
[source]
----
11  Created new transport with session ID: b4115821...
12  Processing request of type CallToolRequest
13  Entering method: wikipedia_search(query='Salsa dance')
14  wikipedia_search: calling wikipedia.summary()
15  wikipedia_search: search succeeded        (~3.8s later — real call to Wikipedia's API)
16  Exiting method: wikipedia_search
17  Processing request of type ListToolsRequest
18  Terminating session: b4115821...
----

The ~4 second gap between lines 39 and 40 (client) / lines 14 and 15 (server) is the *actual* time spent waiting on `wikipedia.summary("Salsa dance", sentences=2)` — a real outbound HTTP call to Wikipedia's API, not overhead from MCP or logging.

The extra `ListToolsRequest` right after the tool call (line 40/17) is issued by the LangChain MCP adapter as part of its per-invocation session bookkeeping before it closes the session — it is not something your code calls explicitly.

=== Step 5 — LLM call #2: "write the final answer"

[source]
----
42  httpx2 POST https://api.openai.com/v1/chat/completions 200 OK   (~1.8s)
----

The agent sends GPT-4o the original question *plus* the Wikipedia summary it just retrieved. GPT-4o now composes the natural-language final answer using that content.

=== Step 6 — Response rendered back to you

[source]
----
43  on_task_submitted: agent.ainvoke() returned response
44  on_task_submitted: rendering full response in Streamlit  -> st.write(response)
45  on_task_submitted: extracted final_output from last message
46  on_task_submitted: rendering final_output in Streamlit    -> st.write(final_output)
47  Exiting method: on_task_submitted
----

== Why it "feels like a lot"

[cols="1,1,3"]
|===
|# |Call type |Purpose

|1 |MCP session (5 requests) |Tool discovery — re-run every Streamlit rerun, even if nothing changed
|2 |OpenAI chat completion |LLM decides *whether/which* tool to call
|3 |MCP session (6 requests) |Actually executes `wikipedia_search` on the server
|4 |OpenAI chat completion |LLM turns tool output into the final natural-language answer
|===

This "2 LLM calls + 1 tool-execution session" pattern is the standard LangChain **ReAct-style agent loop**: think → act (call tool) → think again → answer. It's expected behavior for any single-tool-call agentic question, not a bug. The extra tool-*discovery* session (item 1) is the one avoidable cost — it repeats on every Streamlit rerun because `client.get_tools()` sits at module level instead of being cached.

== Optional improvement (not applied — just noted)

If you want to reduce this to just items 2-4 (skip the redundant discovery round-trip on every rerun), the tool list could be cached with `st.cache_resource` so `get_tools()` only executes once per app session instead of on every keystroke/interaction. == Key difference vs. streamable-http transport

* *HTTP transport*: one persistent server process; client opens/closes lightweight HTTP sessions against it.
* *stdio transport*: no persistent server; **every** interaction (each tool-discovery call and each tool invocation) spawns a **fresh OS subprocess** running `mcp_server_stdio.py` from scratch, importing `wikipedia`/`duckduckgo_search` and re-creating the `FastMCP` instance each time, then exiting after handling exactly one request. This is why `mcp_server_stdio.log` shows 3 separate "Creating FastMCP server instance" blocks for a single question, instead of one continuously-running server.
